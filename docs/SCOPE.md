# Fortune Teller 产品范围

更新日期：2026-08-24

## 1. 产品定位

Fortune Teller 是一个本地优先、可复现、可审计的 Agent Skill 与计算工具箱，用统一工程规则承载中式命理、易占、西洋占星和随机牌卦。

它优先减少三类真正会伤害结果的问题：排盘/起卦不能重算一致、技术事实或传统规则被说错、以及同一盘面被自由改写成互相矛盾的结论。工程改进可以提高计算正确性和传统规则忠实度，但不能据此宣称现实预测效度已经建立。具体做法是：

- 先问用户想看人生整体、某一领域还是当前问题，再选择合适的方法；
- 普通结果固定为“先说结论 → 阶段时间轴（有则显示） → 分主题卡片（结论/白话解读/盘面依据/改判条件/现实提醒） → 现实核对 → 不确定性 → 下一步”，术语和技术记录后置；
- 把机械计算交给固定版本的引擎；
- 把流派、历法、时区、宫制和起卦方式写成显式 profile；
- 把计算事实与传统解释分开；
- 让每条材料性解释绑定适用范围、盘面事实、规则和来源状态；有外部来源时只使用经核验的窄范围记录；
- 只在紫微 `R-ZW-007/008/009` 上开放封闭意义层；另用 24 主星同宫组合、14 本命修饰项和 11 运限修饰项的有界三合规则包读取同宫组合、庙旺、六吉六煞、禄存天马；其他请求不借“深读”名义补造含义；
- 在输入不足时保留不确定性，不静默猜值；
- 让相同输入可复现，让随机过程在用户要求时可回放；
- 默认在本地处理敏感的出生时间、地点和私人问题。

## 2. 用户场景

### 2.1 文化与学习

- 生成结构化盘面或卦面；
- 解释术语、符号和体系内部规则；
- 比较不同 profile 或候选时辰导致的盘面差异；
- 为研究、教学或软件测试导出可复核 facts。

### 2.2 反思与娱乐

- 以塔罗、易卦或传统解释作为组织问题和自我反思的框架；
- 生成非宿命化、带限制说明的叙述；
- 使用安全随机，或在用户明确要求时提供可重放 seed。

### 2.3 Agent 工具调用

- Codex、Claude Code 及其他兼容 Agent Skills 的宿主读取 `SKILL.md`；
- Agent 先收集必要信息，再调用本地引擎；
- Agent 只从结构化 facts 叙述具体盘面，不自行补算；
- 引擎不可用时返回 blocked/error，而不是降级为“凭记忆排盘”。

## 3. 不在产品承诺内

- 不宣称命理、占星、塔罗或易占具有经科学验证的现实预测能力；
- 不比较“谁算得更准”，不宣传预测准确率；
- 不生成或预测升职、录取、离职、结婚、分手、搬迁、横财等具体大事或结果；也不预测死亡日期、重大疾病结果、犯罪、诉讼胜负、投资收益或彩票号码；
- 不用盘面替代医生、律师、财务顾问、心理咨询或现实尽调；
- 不把多个体系结论一致描述为独立证据或因果验证；
- 不在缺少出生时辰、地点或 profile 时生成伪精确结果；
- 不以“覆盖很多方法”为由发布未经测试的空壳入口；
- 不复制竞品代码、提示词、知识库、案例或数据表。

## 5. 发布状态的含义

一个方法只有满足以下条件，才能进入可发布计算路径：

1. 有真实 CLI/工具入口和完整 schema；
2. 同输入、同 profile、同 engine version 的 facts 可复现；
3. 有常规、边界、无效输入和未知时间 fixtures；
4. 叙述忠实度测试阻止模型补造盘面事实；
5. 默认离线，或把任何网络发送字段明确列给用户；
6. 通过干净 archive 的安装与运行检查；
7. 许可证与第三方通知完整。

不满足这些条件时，即使 `methods.mjs` 暂时登记为可用，发布前也必须降为 preview 或 planned。`stable-*` 表示只在后缀所写的口径内稳定；`qualified-*` 表示可以计算，但指定的约定和警告必须贯穿确认、结果和审计，不能对外简称为 `stable`。

## 6. 跨方法统一 contract

所有方法应返回同一顶层 envelope：

- `schema_version`：结果 schema 版本；
- `engine_version`：本项目引擎版本；
- `generated_at`：生成时间，不作为盘面事实；
- `system`：方法 ID；
- `profile`：历法、流派、宫制、起卦法、时区与算法选择；
- `input`：规范化且最小化的输入；
- `facts`：引擎计算或用户确认的事实；
- `warnings`：缺失输入、降级、范围和冲突；
- `sensitivity`：候选时间/profile 下的稳定项与变化项；
- `meta`：上游 engine、版本、时间运行时和随机模式；
- `facts_hash`：后台用于快速比较两份序列化事实是否发生变化的完整性字段；
- `reproducibility_hash`：后台用于比较除生成时间外的完整计算 envelope 是否变化的完整性字段。

重算时应先由同一固定版本引擎回放或做结构复核，再把哈希作为次要的一致性信号。两种哈希都不提高解读准确性，不认证结果来自哪个引擎，也不证明来源或现实预测能力。

自由文本解释不应混入 `facts`。任何“吉凶”“倾向”“建议”若要机器读取，应放在独立的 interpretation 层，并标明它是传统解释而非计算事实。

已知时辰的八字、西占和紫微还会在 `facts.structure` 中返回透明的派生结构：

- 八字：日主、月支上下文、分层不加权计数，以及明确检测到的合冲组合；不得据此偷推旺衰、格局或用神；
- 紫微：完整十二宫索引上的三方四正关系和引擎实际返回的四化位置；不得由单星或索引推出事件；
- 紫微五主题：`facts.topic_units` 将整体、事业学业、财富资源、长期关系、身心节奏分别绑定到主宫、完整三方四正和属于该单元的四化；主题解释不得从其他单元抽取方便的事实；
- 紫微显式目标日期：`facts.periods` 返回大限和流年宫位映射、运限星与四化；封闭层按两个 scope 分别派生 `[0,+4,+8,+6]` 动态四宫，不含流月/流日/流时或必然事件；
- 紫微封闭意义层：`fortune-teller/ziwei-meaning-binding/v2` 为 `R-ZW-007/009` 读取四宫十四主星轴、同宫组合、庙旺、六吉六煞、禄存天马；本命主星的 `star_in_palace` 携带 `brightness`。意义登记表为 5 主题/14 主星双向轴/4 四化过程镜头，三合结果规则包另登记 24 主星组合/14 本命修饰项/11 运限修饰项。`R-ZW-008` 纳入全部本命四化。`R-ZW-009` 按本命底色→大限环境→流年触发展开；大限与流年各有四个动态槽 `[0,+4,+8,+6]`，已登记运限星用 `period_star_in_slot` 完整绑定。阶段四化仍只覆盖精确主题宫动态槽；大限与流年集合都存在且完整纳入，两层合计至少一项，单层可空。正式标准联合要求本命焦点轴、大限四槽全部条件、流年四槽全部条件与主题槽全部四化过程，三层不能互相替代。窗口是两条记录均不变且两端可完整重放的最大连续区间。这不是四宫阶段四化会照或完整紫微论断；
- 西占：不加权元素/模式计数、关键点引用、2° 内相位的展示优先级和宫位占用计数；不得转成优势、尊贵、人格或预测分数。

`src/data/source-registry.mjs` 记录经核验的实现或历史来源及其窄范围限制；`src/data/rule-registry.mjs` 记录规则允许的 system、scope、可计数 fact-ID 根与少量明确登记的材料性标量路径、最低事实数量、复合规则必须逐组满足的事实、必要事实值、来源组合与解释上限。`src/data/interpretation-profile-registry.mjs` 固定每个解读档案允许的计算口径和完整规则包；`src/data/meaning-registry.mjs` 固定三条紫微深层路径能用的封闭含义。`bind-reading` 将阅读绑定到精确计算及事实值，为六体系技术断言机械生成类型化摘要，并在紫微 `R-ZW-007/008/009` 上覆写完整含义正文与标准。`validate-reading` 先重算计算 facts，再独立重算技术和紫微含义绑定，拒绝旧盘套新解、证据替换、重复事实 ID、正文反说技术事实、紫微跨主题拼接和改写封闭正文。三条封闭路径之外的自由叙事仍保持 `not_machine_verified`；通过验证也不等于独立专家认证或预测有效。

## 7. 输入与时间政策

### 7.1 不猜输入

- 不知道出生时间就保存为未知；用户给出的范围保留在对话中，但当前 schema 不把它伪装成原生计算字段；
- `time_precision` 由输入钟表格式规范化为 `minute`、`second` 或 `unknown`；它记录文字精度，不证明出生记录本身准确；
- 不知道地点就不启用需要经纬度的校正；
- 不知道时区就追问 IANA timezone，不只接收含糊的“北京时间附近”；
- 当前核心出生盘不直接接收农历出生日期；如果用户只有农历记录，须在独立核验步骤换算为公历，并保留是否闰月和换算来源；
- 用户已有盘面时，可把它作为 `user-confirmed` 事实，但不得冒充本引擎计算结果。

### 7.2 真太阳时

八字当前只支持民用时间；mean-solar 与 apparent-solar 八字 profile 已禁用，因为年/月节气边界尚不能与本地日/时计算安全拆分。任何 UTC+08:00 以外的实际时刻都必须报 `UNSUPPORTED_BAZI_CALENDAR_OFFSET`，不得手动平移钟表时间绕过。

紫微也只支持民用时间；mean-solar/apparent-solar override 已禁用，直到 `birthplace-civil` 日历日选择和本地时辰索引能用两套明确时钟分开表达。UTC+08:00 以外仍必须标记为流派/口径限定。西占当前没有把“真太阳时”作为本命盘输入 profile。

### 7.3 候选时辰

对八字、紫微、西占等敏感方法，候选时辰模式应输出：

- 所有候选都相同的稳定事实；
- 随候选改变的字段；
- 因输入不足无法回答的问题；
- 用户可用于缩小范围的非诱导性信息。

不得用事后“套经历”的方式把一个时辰包装成客观确认。

## 8. 随机方法政策

- 默认使用操作系统安全随机；
- 用户提供实体牌或硬币结果时优先尊重用户输入，不再次随机；
- replay seed 只用于复盘、教学和测试，不宣称更灵验；
- 默认只输出 seed commitment；只有 fresh 本地抽取时用户显式设置 `reveal_seed:true` 才回显可重放 seed，且工具本身不持久化它；
- 随机算法、牌组版本、牌阵和正逆位规则写入 profile；
- 统计测试只验证抽样实现，没有取模偏差或明显故障。
- 同一问题的追问复用冻结的牌面或卦面；换成新问题时必须明确确认重新抽牌/起卦，不能因为用户说“不准”就自动重抽。

## 9. 叙述与安全边界

面向普通用户的结果按以下固定层级组织：

1. 先说直接、条件性的综合结论；summary 按句拆成要点；
2. 若有精确阶段，紧接着显示时间轴，结论只用类别级白话，详细星曜留在依据层；
3. 分主题卡片；每张按“结论 → 白话解读 → 盘面依据（术语） → 什么情况要改判 → 现实提醒”；
4. 显示现实支持/反驳/不清楚核对，再显示不确定性与下一步；
5. 白话按句、术语依据按分号、改判条件逐条拆为 bullet；
6. 术语表、完整盘面/牌面、来源、profile、warning、候选数量、内部完整性字段和原始 JSON 技术记录后置到高级入口。

所有解释性 claim 都必须引用至少一条适用的登记规则；没有规则覆盖时只能展示计算事实或标为未解决。claim 不接受自由文本 `dependencies`；输入限制只能由计算确定性、资料敏感性或明确的未解决说明表达。`standard`、`deep` 与 `audit` 的 `next_steps` 必须是结构化动作，明确是否可用、还需什么输入、是否复用冻结计算；显示标签和不可用原因由 binder 固定生成。binder 同时固定标题、按全部 claim 顺序去重后的 `user_focus`、非预测说明、不确定性摘要和精确材料 warning code 集合。单体系必须省略 `cross_system`；多体系固定为 `{relationship: "not_compared"}`，当前不声称机器能判断体系间同构、互补或冲突。深度与审计 reading 还必须提供每条 claim 的推理摘要和至少一个其他读法。修改输入或 profile 后，绑定旧计算的解释立即失效，不得沿用。

用户想做正式核验时，只能选择已通过验证的紫微 `R-ZW-009` 三层主题突出度 `prospective_hypothesis`。正式标准联合要求本命焦点组全部主星轴、大限四个动态槽的全部已登记运限星条件、流年四个动态槽的全部已登记运限星条件，以及精确主题槽的全部大限/流年四化过程；三层不能互相替代。窗口必须是当前 profile 下两条记录都不变且两端能完整括定的精确连续区间。四宫阶段四化会照、泛化领域活跃、具体事件、其他规则或体系均不接受。窗口结束后才逐 criterion 登记观察，并由工具机械派生结果。已知结局只作非正式反馈；三条封闭路径之外的 claim 不得写未来事件断言。

对健康、法律、财务、心理危机等高风险主题，传统解释只能作为文化参考，必须把现实专业支持放在前面。禁止恐吓、收费化解暗示、债务/疾病/死亡断言和保证性语言。

## 10. 隐私范围

- 默认本地计算；
- 默认不持久化生辰、精确地点和问题文本；
- 日志只保留必要的错误码、版本和匿名 fixture ID；
- 如未来增加地理编码、MCP 或 HTTP API，必须逐字段告知将发送什么；
- 报告导出默认提醒用户其内容可能包含敏感个人信息；
- 测试和示例只用虚构资料或明确授权的公开资料。

## 11. 路线图

### Phase 0 — 可信核心（已随 0.2.0 交付）

- 完成 Skill frontmatter 与任务路由；
- 固定统一输入/输出/error schema；
- 为 envelope、引擎重算、随机回放、后台完整性字段和方法注册补单元测试；
- 建立 `doctor`、release check、第三方通知和 clean archive 验证；
- 让每个登记为可发布的限定状态达到 `BENCHMARK.md` 的 releasable 等级，否则降级标签。

### Phase 1 — 当前核心方法（已随 0.2.0 交付，按本文件边界）

## 12. 相对竞品的目标与差距

### 目标做得更好的方面

这里的“更好”是可测试目标，不是当前无条件结论：

- 比远程 API 型项目更清楚地默认本地和最小化敏感数据；
- 比 prompt-only 项目更严格地禁止模型自行排盘；
- 比只返回文本的项目更强调固定引擎重算、统一 facts、类型化技术断言和显式 sensitivity；
- 比不可回放的随机抽取提供安全随机与用户选择的可回放模式；
- 比超宽单体 Skill 更明确地区分方法状态和失败条件；
- 让中式与西式方法接受同一套可复现和叙述忠实度要求。

### 仍然落后的方面

- 方法数量远少于 Horosa、Chinese Fortune、Mingyu 和 dhicoc；
- 六爻、奇门和吠陀仍处于 planned；
- 尚无黄历、风水、姓名、大六壬、太乙等常见中式模块；
- 尚无成熟 MCP/API/Dashboard 和多格式报告；
- 测试量、外部用户、案例库、知识来源深度尚未达到第一梯队；
- 当前依赖上游计算库，必须建立自己的封装 parity 与升级审计。

项目应公开这些差距，不用“全能大师”“最准”“科学算命”等不可核验词汇掩盖范围限制。

# Fortune Teller 产品范围

更新日期：2026-08-23

## 1. 产品定位

Fortune Teller 是一个本地优先、可复现、可审计的 Agent Skill 与计算工具箱，用统一工程规则承载中式命理、易占、西洋占星和随机牌卦。

它的核心价值不是证明或提高预测准确性，而是：

- 把机械计算交给固定版本的引擎；
- 把流派、历法、时区、宫制和起卦方式写成显式 profile；
- 把计算事实与传统解释分开；
- 在输入不足时保留不确定性，不静默猜值；
- 让相同输入可复现，让随机过程在用户要求时可回放；
- 默认在本地处理敏感的出生时间、地点和私人问题。

## 2. 用户场景

### 2.1 文化与学习

- 生成结构化盘面或卦面；
- 解释术语、符号和体系内部规则；
- 比较不同 profile 或候选时辰导致的盘面差异；
- 为研究、教学或软件测试导出可复核 facts。

### 2.2 反思与娱乐

- 以塔罗、易卦或传统解释作为组织问题和自我反思的框架；
- 生成非宿命化、带限制说明的叙述；
- 使用安全随机，或在用户明确要求时提供可重放 seed。

### 2.3 Agent 工具调用

- Codex、Claude Code 及其他兼容 Agent Skills 的宿主读取 `SKILL.md`；
- Agent 先收集必要信息，再调用本地引擎；
- Agent 只从结构化 facts 叙述具体盘面，不自行补算；
- 引擎不可用时返回 blocked/error，而不是降级为“凭记忆排盘”。

## 3. 不在产品承诺内

- 不宣称命理、占星、塔罗或易占具有经科学验证的现实预测能力；
- 不比较“谁算得更准”，不宣传预测准确率；
- 不预测死亡日期、重大疾病结果、犯罪、诉讼胜负、投资收益或彩票号码；
- 不用盘面替代医生、律师、财务顾问、心理咨询或现实尽调；
- 不把多个体系结论一致描述为独立证据或因果验证；
- 不在缺少出生时辰、地点或 profile 时生成伪精确结果；
- 不以“覆盖很多方法”为由发布未经测试的空壳入口；
- 不复制竞品代码、提示词、知识库、案例或数据表。

## 5. “stable” 的含义

一个方法只能在用户文档中称为 stable，当它：

1. 有真实 CLI/工具入口和完整 schema；
2. 同输入、同 profile、同 engine version 的 facts 可复现；
3. 有常规、边界、无效输入和未知时间 fixtures；
4. 叙述忠实度测试阻止模型补造盘面事实；
5. 默认离线，或把任何网络发送字段明确列给用户；
6. 通过干净 archive 的安装与运行检查；
7. 许可证与第三方通知完整。

不满足这些条件时，即使 `methods.mjs` 暂时写为 stable，发布前也必须降为 preview 或 planned。

## 6. 跨方法统一 contract

所有方法应返回同一顶层 envelope：

- `schema_version`：结果 schema 版本；
- `engine_version`：本工作台封装版本；
- `generated_at`：生成时间，不作为盘面事实；
- `system`：方法 ID；
- `profile`：历法、流派、宫制、起卦法、时区与算法选择；
- `input`：规范化且最小化的输入；
- `facts`：引擎计算或用户确认的事实；
- `warnings`：缺失输入、降级、范围和冲突；
- `sensitivity`：候选时间/profile 下的稳定项与变化项；
- `meta`：上游 engine、版本、时间运行时和随机模式；
- `facts_hash`：对 engine version、system、profile 与实际计算/抽取事实的承诺，用于比较事实是否相同；
- `reproducibility_hash`：对除生成时间外的完整审计 envelope 的承诺，包含输入、warnings、sensitivity、来源和运行时信息。

自由文本解释不应混入 `facts`。任何“吉凶”“倾向”“建议”若要机器读取，应放在独立的 interpretation 层，并标明它是传统解释而非计算事实。

## 7. 输入与时间政策

### 7.1 不猜输入

- 不知道出生时间就保存为未知；用户给出的范围保留在对话中，但 v0.1 不把它伪装成原生计算字段；
- 不知道地点就不启用需要经纬度的校正；
- 不知道时区就追问 IANA timezone，不只接收含糊的“北京时间附近”；
- v0.1 不直接接收农历出生日期；如果用户只有农历记录，须在独立核验步骤换算为公历，并保留是否闰月和换算来源；
- 用户已有盘面时，可把它作为 `user-confirmed` 事实，但不得冒充本引擎计算结果。

### 7.2 真太阳时

真太阳时是可选 profile，不是默认“纠错”。只有经度、民用时区、历史夏令时和换算规则均明确时才计算。资料不足时不得静默退回民用时间；应让用户明确选择民用 profile，或报告该太阳时计算不可用。

### 7.3 候选时辰

对八字、紫微、西占等敏感方法，候选时辰模式应输出：

- 所有候选都相同的稳定事实；
- 随候选改变的字段；
- 因输入不足无法回答的问题；
- 用户可用于缩小范围的非诱导性信息。

不得用事后“套经历”的方式把一个时辰包装成客观确认。

## 8. 随机方法政策

- 默认使用操作系统安全随机；
- 用户提供实体牌或硬币结果时优先尊重用户输入，不再次随机；
- replay seed 只用于复盘、教学和测试，不宣称更灵验；
- 默认只输出 seed commitment；只有 fresh 本地抽取时用户显式设置 `reveal_seed:true` 才回显可重放 seed，且工具本身不持久化它；
- 随机算法、牌组版本、牌阵和正逆位规则写入 profile；
- 统计测试只验证抽样实现，没有取模偏差或明显故障。

## 9. 叙述与安全边界

面向用户的结果按以下顺序组织：

1. 输入与 profile；
2. 可复核盘面/卦面事实；
3. 传统体系内的解释；
4. 不确定性与其他可能读法；
5. 非宿命化的反思问题或现实建议；
6. 简短免责声明。

对健康、法律、财务、心理危机等高风险主题，传统解释只能作为文化参考，必须把现实专业支持放在前面。禁止恐吓、收费化解暗示、债务/疾病/死亡断言和保证性语言。

## 10. 隐私范围

- 默认本地计算；
- 默认不持久化生辰、精确地点和问题文本；
- 日志只保留必要的错误码、版本和匿名 fixture ID；
- 如未来增加地理编码、MCP 或 HTTP API，必须逐字段告知将发送什么；
- 报告导出默认提醒用户其内容可能包含敏感个人信息；
- 测试和示例只用虚构资料或明确授权的公开资料。

## 11. 路线图

### Phase 0 — 可信核心

- 完成 Skill frontmatter 与任务路由；
- 固定统一输入/输出/error schema；
- 为 envelope、哈希、随机回放和方法注册补单元测试；
- 建立 `doctor`、release check、第三方通知和 clean archive 验证；
- 让注册为 stable 的每个方法达到 `BENCHMARK.md` 的 releasable 等级，否则降级标签。

### Phase 1 — 当前核心方法

- 八字、紫微、西占 whole-sign 的引擎封装与边界 fixtures；
- 塔罗和三钱起卦的安全随机、用户实抽输入与 replay；
- 统一 facts/interpretation/sensitivity 输出；
- 中文和英文的最小可用报告。

### Phase 2 — Preview 与计划方法

- 梅花：固定数字起卦和时间起卦 profile，补 golden fixtures 后再转 stable；
- 六爻：先实现装卦事实层，再单独建设解读 references；
- 奇门：先选定有限 profile 和结构化九宫 schema，不以“支持所有流派”为目标；
- 吠陀：只有固定 ayanamsa、宫制和星历 parity 后才开放。

### Phase 3 — 扩展能力

只有核心发布门稳定后再评估：

- 黄历择日、风水、姓名学；
- 大六壬、太乙、小六壬、金口诀；
- 西占合盘、推运、择时与更多宫制；
- MCP、HTTP API、Dashboard、图盘与 HTML/PDF 报告。

这些扩展不是当前版本承诺。

## 12. 相对竞品的目标与差距

### 目标做得更好的方面

这里的“更好”是可测试目标，不是当前无条件结论：

- 比远程 API 型项目更清楚地默认本地和最小化敏感数据；
- 比 prompt-only 项目更严格地禁止模型自行排盘；
- 比只返回文本的项目提供统一 facts、profile、sensitivity 和 reproducibility hash；
- 比不可回放的随机抽取提供安全随机与 seed commitment；
- 比超宽单体 Skill 更明确地区分方法状态和失败条件；
- 让中式与西式方法接受同一套可复现和叙述忠实度要求。

### 仍然落后的方面

- 方法数量远少于 Horosa、Chinese Fortune、Mingyu 和 dhicoc；
- 六爻、奇门和吠陀仍处于 planned；
- 尚无黄历、风水、姓名、大六壬、太乙等常见中式模块；
- 尚无成熟 MCP/API/Dashboard 和多格式报告；
- 测试量、外部用户、案例库、知识来源深度尚未达到第一梯队；
- 当前依赖上游计算库，必须建立自己的封装 parity 与升级审计。

项目应公开这些差距，不用“全能大师”“最准”“科学算命”等不可核验词汇掩盖范围限制。
